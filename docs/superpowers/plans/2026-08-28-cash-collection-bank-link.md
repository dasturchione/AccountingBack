# Cash Collection and Bank Operation Link Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement cash collection documents from draft through cash-in-transit, connect the confirming bank statement operation, and expose CRUD plus a compact list of collections awaiting bank confirmation.

**Architecture:** `cash_collection_doc` owns the cash-to-transit stage. A nullable `bank_operation.cash_collection_doc_id` owns the later match from the bank statement; confirming that operation completes the collection, and cancelling the posted operation returns it to `IN_TRANSIT`. Accounting and money-register effects remain separated by document type so that each stage can be reversed independently.

**Tech Stack:** .NET 10, ASP.NET Core, EF Core, PostgreSQL, FluentValidation, xUnit.

**Spec:** Agreed conversation design: one active bank operation per cash collection, exact organization/bank account/currency/amount match, no direct bank balance increase before bank-operation confirmation.

## Global Constraints

- SQL uses `serial`/`bigserial`, `int`, `varchar`, and inline `references` declarations.
- Document numbers are generated by `IDocumentNumberService` and restart per organization and calendar year.
- No manual document-number input.
- Do not commit changes unless the user explicitly requests a commit.
- Existing unrelated working-tree changes must remain untouched.
